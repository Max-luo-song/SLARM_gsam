# SLARM 代码阅读教程：借助 AI 抓住主干与关键细节

这份教程面向“需要真正理解项目，但不打算逐行阅读”的读者。目标不是记住每个类，而是建立一个能解释、调试和修改 SLARM 的心智模型。

本文基于当前仓库代码编写。阅读时应以代码为最终事实，README 和论文用于理解设计动机。

## 1. 先用一句话理解项目

SLARM 接收稀疏时刻的多相机图像、相机内外参和时间，直接预测一组带运动与语义特征的 3D Gaussians，再把它们移动到目标时刻并渲染到目标相机，从而同时完成动态场景重建、新视角/新时刻合成、场景流估计和文本语义查询。

可以把完整过程压缩为：

```text
多时刻、多相机图像 + 相机参数 + 时间
                  |
                  v
       时空 Transformer Aggregator
                  |
       +----------+----------+
       |          |          |
       v          v          v
 3D Gaussian   运动参数    语义特征
   参数头       预测头       预测头
       \          |          /
        +---------+---------+
                  |
          按目标时间移动 Gaussian
                  |
          gsplat / NPU 光栅化
                  |
                  v
      RGB、深度、场景流、语义特征
```

最重要的设计选择是：每个上下文像素基本对应一个 Gaussian。网络先预测该 Gaussian 在参考坐标系中的位置、形状、颜色和透明度，再预测它随时间如何运动。目标图像不是普通 decoder 直接生成的，而是由这些 Gaussians 经可微渲染得到。

## 3. 四个入口分别回答什么问题

### 3.1 训练：`main_slarm.py`

先搜索以下锚点：

```bash
rg -n "def get_args_parser|def main|prepare_inputs_and_targets|pred_dict = model|compute_loss" main_slarm.py
```

主链只有五步：

```python
dataset -> DataLoader
input_dict, target_dict = prepare_inputs_and_targets(...)
pred_dict = model(input_dict)
loss_dict = compute_loss(pred_dict, input_dict, target_dict, ...)
loss_scaler(sum(losses), optimizer, ...)
```

其余代码主要处理分布式、日志、checkpoint、定期可视化和评估。第一次阅读时，把这些看成训练框架的外壳即可。

### 3.2 离线推理：`inference.py`

它使用 `SingleSequenceDataset` 读取指定场景的一段连续帧，随后由 `make_video` 驱动模型并生成视频。它适合回答“整段 clip 的结果如何生成”，但模型调用被封装在可视化代码中，所以不适合作为第一次理解 `forward` 的入口。

### 3.3 流式推理：`inference_stream.py`

它将 context 按单帧拆开，反复调用：

```python
predictions = session.forward_stream(one_frame_dict, device, dtype)
```

`StreamSession` 保存 attention 的 KV cache，并把各帧预测沿时间维拼起来。理解流式模式时必须同时阅读 `src/models/stream_session.py`，不能只看推理脚本。

### 3.4 文本查询：`text_query_visualizing.py`

它先正常预测 `rendered_feat`，再把文本编码成 CLIP/LSeg 对齐的向量，计算余弦相似度，最后执行高亮或全量分割。关键不是“额外训练一个分类器”，而是比较像素/ Gaussian 的开放词汇特征与文本特征。

## 4. 第一条主线：数据如何变成模型输入

### 4.1 标注文件是索引，不是训练样本本身

`PerceptualModelDataset.__init__` 先读取 scene-list 文本文件。每一行指向一个场景 JSON，然后加载 JSON 中的：

- 各相机图像相对路径；
- 相机到世界坐标的变换；
- 归一化内参；
- 帧数、FPS 和归一化时间；
- 场景与数据集名称。

真正的 RGB、深度、流、天空 mask 和语义标签由 `get_frame()` 按约定目录读取。排查“文件找不到”时，必须跟踪 `img_path.replace(...)` 形成的派生路径，而不能只检查 JSON。

### 4.2 context 与 target 的含义

在 `get_segment()` 中：

- context 是模型实际看见的稀疏帧；
- target 是用于渲染监督的目标帧；
- 默认 `equispaced=True`，context 在 `timespan` 内等间隔采样；
- 默认 `only_interp=True`，target 位于首尾 context 之间；
- 训练时 target 从候选帧中随机取 `num_target_timesteps` 个；
- context 和 target 都包含多个相机视角。

例如默认 `T=4, V=3` 时，dataset 内部先把图像组织成 `[T*V, C, H, W]`。`prepare_inputs_and_targets()` 再恢复时间和相机两个轴。

### 4.3 必须记住的张量符号

本文统一使用：

| 符号 | 含义 | 默认示例 |
| --- | --- | --- |
| `B` | batch size | 每卡由 `--batch_size` 决定 |
| `T` | context 时间数 | 4 |
| `V` | 每个时间的相机数 | 3 |
| `Tq` | target 时间数 | 训练默认 4，推理可更多 |
| `H, W` | 图像高宽 | 常见为 160, 240 |
| `D` | Transformer embedding 维度 | 示例脚本为 768 |
| `F` | 语义特征维度 | 模型默认 64 |

核心输入形状：

```text
context_image        [B, T,  V, 3, H, W]
context_camtoworlds  [B, T,  V, 4, 4]
context_intrinsics   [B, T,  V, 3, 3]
context_time         [B, T,  V]

target_camtoworlds   [B, Tq, V, 4, 4]
target_intrinsics    [B, Tq, V, 3, 3]
target_time          [B, Tq, V]
target_image         [B, Tq, V, 3, H, W]
```

一个关键细节：时间先在 dataset 中变成“相对首个 context 帧的时间”，再在 `prepare_inputs_and_targets()` 中除以 `timespan`。渲染时又乘回 `timespan`。因此调试运动时，必须区分归一化时间与秒。

### 4.4 坐标系不能略读

`get_frame()` 以第一个 context 时刻的参考相机作为 canonical frame，并组合：

```text
dataset canonical -> world_to_canonical -> camera_to_world -> OpenCV/dataset 轴变换
```

项目在 `src/dataset/constants.py` 中明确使用 FLU 约定：`x` 向前、`y` 向左、`z` 向上。深度生成点、场景流旋转和相机外参都依赖这个约定。若出现“几何正确但方向旋转 90 度”一类问题，优先检查此处。

## 5. 第二条主线：Aggregator 如何融合时空信息

从 `SLARM.forward()` 进入后，最重要的一句是：

```python
output_list, patch_start_idx = self.aggregator(data_dict, mode=self.mode)
```

`Aggregator.forward()` 可按四段理解。

### 5.1 从图像生成 patch token

输入图像先按 ImageNet mean/std 归一化。根据配置，patch embedding 可以是卷积，也可以是 DINOv2/Vision Transformer 风格的模块。

相机射线以 Plucker 坐标编码，每条 ray 用方向 `d` 与矩 `o x d` 表示，共 6 维。代码支持两种注入方式：

- `concat_plucker_embed`：在通道维与 RGB 拼接后再 patchify；
- `add_patch_plucker_embed`：把 patch 级 Plucker 编码线性投影后加到视觉 token。

示例脚本启用的是后者。阅读配置时不要把“代码支持”误认为“当前实验启用”。

### 5.2 special tokens

patch token 之前可能存在：

- camera token；
- register tokens；
- time token；
- motion tokens；
- 每个相机的 affine token；
- sky token。

`patch_start_idx` 是这些 token 总数，也是后续将 special token 与图像 patch 分开的边界。修改 token 配置时，所有切片顺序都要一起检查；`SLARM.forward()` 是从尾部按 `sky -> affine -> motion -> time` 的顺序取回它们。

### 5.3 交替 attention

Aggregator 为每层维护两组 block：

- frame attention：单帧/单视角内部交互；
- global attention：跨时间和视角融合。

两者按 `aa_order=["frame", "global"]` 交替执行。模型保留若干中间层输出，供 DPT 深度、点图或 dense head 使用；启用 `--use_last_token` 时，Gaussian、motion 和 feature head 主要直接消费最后一层 patch token。

### 5.4 full、causal 与 window

- `full`：所有时刻可互相注意，适合普通训练/离线推理；
- `causal`：当前时刻只能利用过去与当前信息；
- `window_N`：只保留长度为 `N` 的滑动窗口。

模式不仅影响 attention mask，还影响后续 Gaussian 在哪些时间范围内有效。不要把它理解为单纯的显存优化开关。

## 6. 第三条主线：一个像素如何变成动态 3D Gaussian

### 6.1 Gaussian 参数

`forward_gs_predictor()` 将预测通道拆为：

| 字段 | 最后一维 | 含义 |
| --- | ---: | --- |
| `depth` | 1 | 沿输入 ray 的深度 |
| `scales` | 3 | 三轴尺度 |
| `quats` | 4 | 旋转四元数 |
| `opacities` | 1 | 不透明度 |
| `colors` | `gs_dim` | 通常为 RGB |
| `confs` | 1，可选 | voxel 聚合权重 |
| `lifespans` | 1，可选 | 时间有效范围 |

激活后的位置由下式获得：

```text
means = ray_origin + ray_direction * depth
```

因此网络并非无约束地回归世界坐标，而是在已知相机 ray 上回归深度。只有启用 `--use_pred_camera_pose` 或 `--use_pred_depth` 时，ray 或 depth 才分别改用 camera/depth head 的预测；否则使用输入真值相机和 Gaussian head 自己预测的深度。

主要输出的形状为：

```text
means       [B, T, V, H, W, 3]
scales      [B, T, V, H, W, 3]
quats       [B, T, V, H, W, 4]
opacities   [B, T, V, H, W]
colors      [B, T, V, H, W, 3]
```

这里的 `H, W` 最终会被 head 上采样回像素网格大小，所以 Gaussian 数量约为 `T * V * H * W`。这也解释了渲染阶段为何是显存与性能热点。

### 6.2 RGB shortcut

示例配置使用 `--shortcut_rgb`。此时输入 RGB 会与 head 预测特征拼接，再回归 Gaussian 参数。它允许颜色重建直接利用观测图像，而不必完全由抽象 token 重新生成。

### 6.3 运动预测有两种路线

当 `num_motion_tokens > 0` 时，代码将每个像素分配给若干 motion basis：像素 key 与 motion token query 做点积、softmax 得到 `motion_weights`，再对 motion bases 加权。

示例脚本设置 `--num_motion_tokens 0`，因此跳过 basis 分解，由像素特征直接预测运动。

启用 `--use_ms3_motion` 后，预测的不是单一速度，而是三阶运动系数。对时间差 `dt`，平移近似为：

```text
offset(dt) = a1 * dt + a2 * dt^2 / 2! + a3 * dt^3 / 3!
```

代码再用当前与前一帧 offset 的差估计渲染场景流。这个细节很重要：`forward_ms3` 是多项式系数，`rendered_flow` 才是特定目标时刻/视角下渲染出的流，二者不能直接比较。

### 6.4 语义特征

`forward_feat_predictor()` 为每个输入像素预测 `pred_feat`，并用 sigmoid 激活。训练时它与在线 LSeg 特征做 MSE、余弦距离或类别概率监督；渲染时语义特征像颜色一样随 Gaussian 投影到目标视角。

开放词汇查询的链路是：

```text
文本 -> CLIP/LSeg 文本向量
目标像素 -> rendered_feat
余弦相似度 -> 阈值/argmax -> 高亮或分割
```

## 7. 第四条主线：动态 Gaussian 如何渲染到目标帧

`SLARM.forward_renderer()` 是理解项目算法的核心函数之一。

### 7.1 展平并复制

所有 context Gaussian 从 `[B,T,V,H,W,*]` 展平为 `[B,T*V*H*W,*]`，再为每个 target 时间复制一份。随后计算每个 target 与每个 source Gaussian 的时间差。

### 7.2 将 Gaussian 移到目标时刻

普通速度模式使用：

```text
target_mean = source_mean + velocity * dt
```

MS3 模式使用上一节的多项式。可选角速度会进一步更新四元数。`lifespan` 开启时还会按时间差衰减 opacity。

在 causal/window 模式下，代码额外构造时间 mask：动态 Gaussian 只在受允许的时间段贡献渲染；接近静止的 Gaussian 可以覆盖稍后的区间。这部分同时决定了流式重建是否出现重影。

### 7.3 可微光栅化

渲染后端由运行平台决定：

- GPU：`gsplat.rendering.rasterization`；
- Ascend NPU：根据 `RENDER_OP_VERSION` 选择仓库内 rasterizer 或 `meta_gauss_render`。

送入 rasterizer 的核心属性是 `means/scales/quats/opacities/colors`，相机使用 target 的外参逆矩阵和内参。`render_mode="RGB+ED"` 同时返回颜色和 expected depth。

训练与评估的通道存在一个容易漏掉的差异：训练时通常只拼 RGB（以及可选 feature）；非训练模式还会把 `forward_v` 拼进 colors 一起 rasterize，从而得到 `rendered_flow`。

### 7.4 天空与曝光修正

Gaussian 渲染之后还有两个后处理分支：

- sky token 根据 target ray 生成天空颜色，再以 `(1 - alpha)` 填补未被 Gaussian 覆盖的区域；
- affine token 为每个相机预测颜色线性变换与平移，修正多相机曝光/色彩差异。

所以 `rendered_image` 不一定等于 rasterizer 的原始 RGB。遇到颜色偏差时，需要分别检查 Gaussian color、sky 合成和 affine 修正。

## 8. 第五条主线：训练到底优化什么

训练循环最终把 `compute_loss()` 中所有 key 含 `loss` 的值相加。主要损失包括：

| 损失 | 监督对象 | 典型开关 |
| --- | --- | --- |
| RGB/LPIPS | target 渲染图像 | `rgb_loss_coeff`、`enable_perceptual_loss` |
| target depth | 渲染深度 | `enable_depth_loss` |
| context depth/point | 辅助 head | `enable_context_*_loss` |
| sky opacity/depth | 天空区域 | `enable_sky_opacity_loss` 等 |
| flow | target 场景流 | `enable_flow_loss` |
| flow regularization | Gaussian 运动趋近静态 | `enable_flow_reg_loss` |
| semantic feature | LSeg 特征 | `enable_feat_loss` / `enable_context_feat_loss` |
| camera pose | camera head | `enable_camera_loss` |
| lifespan regularization | Gaussian 生命周期 | `enable_lifespan_reg_loss` |

示例训练脚本中的重点组合是 RGB、深度、天空透明度、运动正则和感知损失，并按 GPU/NPU 选择 target feature 或 context feature 监督。

三个关键细节：

1. `context_prediction_loss_warmup_steps` 之前可以只训练 context 辅助预测，提前从 `compute_loss()` 返回。
2. LPIPS 在 `perceptual_loss_start_iter` 之后才打开。
3. `rgb_mse` 用来计算 PSNR，但总损失按 key 是否包含 `loss` 汇总；新增指标时不要误把名字写成 `*_loss`。

## 9. 流式推理必须单独理解

离线 full attention 一次看到整个 clip；流式推理每次只送入一个 context 时刻，并依靠 KV cache 避免重复计算历史。

`StreamSession` 管理两类状态：

```text
计算状态：aggregator_kv_cache_list、camera_head_kv_cache_list
输出状态：gs_params、pred_feat、camera/depth/point 预测、sky/affine token
```

每次 `forward_stream()`：

1. 取出旧 cache；
2. 调用 `model(..., aggregator_kv_cache_list=..., camera_head_kv_cache_list=...)`；
3. 将当前帧预测拼到历史预测；
4. 更新 cache；
5. 返回累计预测。

causal 模式保留全部历史 cache。window 模式会删除最旧一帧对应的 aggregator token，以及 camera head cache 的最旧位置，从而保持固定窗口。

需要特别留意：`sky_token`、`affine_tokens` 和 `motion_bases` 当前采用“最后一次预测覆盖历史”的策略，代码中也标了 TODO。这意味着它们不是逐帧独立保存的。

`inference_stream.py` 中 `time_step=5` 表示相邻 context 帧相隔 5 个原始帧；每个 context 对应的一段 target 会在后处理中重新组合。不要把 `window_3` 误解成只输出 3 个视频帧，它指的是 attention/cache 的 context 窗口长度。

## 10. 配置不是附属信息，而是实际模型定义

阅读时把 `training.sh` 或当前使用的实验脚本与 `get_args_parser()` 并排打开。默认值只是兜底，真正结构由命令行共同决定。

以下参数会改变模型结构或主数据流：

```text
--embed_dim --depth --patch_size --patch_embed
--use_last_token --shortcut_rgb
--use_ms3_motion --num_motion_tokens --add_angular_velocity
--use_sky_token --use_affine_token
--enable_camera_head --use_pred_camera_pose
--enable_depth_head --use_pred_depth
--online_feat --without_feat
--mode
```

环境变量也会改变代码路径：

| 环境变量 | 影响 |
| --- | --- |
| `DEVICE_TYPE` | GPU/NPU 路径选择 |
| `RENDER_OP_VERSION` | NPU rasterizer 版本 |
| `FEAT_DIST` | 是否导入文本/语义工具 |
| `CONTEXT_FEAT` | 在 context 而非 target 监督语义特征，并禁止渲染 feature |
| `OVERFIT_EXP` | 改写数据集 scene-list 选择 |
| `SCENE_ID_WAYMO` | 单场景实验的索引 |
| `DISABLE_BFLOAT` | 使用 fp16 而非 bf16 |
| `DATASET_SAMPLE_NUMS` | 多数据集采样量 |

尤其要注意 `src/dataset/constants.py` 在 import 时就会读取部分环境变量，甚至生成单场景 scene-list 文件。调试配置时，应先确认 shell 环境，再启动 Python。

## 11. 建议的六轮阅读法

### 第一轮：30 分钟建立地图

阅读 `README.md`、一个实际运行脚本、`main_slarm.py:get_args_parser()` 和本教程。输出一张自己的“输入 -> 模型 -> 渲染 -> loss”图。

完成标准：能说清 context 与 target 的区别，以及训练、离线推理、流式推理三个入口。

### 第二轮：45 分钟追踪一个 batch

依次阅读：


## 12. 怎样让 AI 真正帮你读，而不是复述代码

### 12.1 每次给 AI 一个闭环

低效提问：

```text
解释 slarm.py。
```

更好的提问：

```text
请追踪 src/models/slarm.py 中 context_image 从进入 SLARM.forward 到生成
rendered_image 的完整调用链。每一步列出函数、输入/输出 shape、坐标系和时间含义；
区分由当前配置启用的分支与仅仅存在于代码中的可选分支。不要逐行复述。
```

一次只追一条链：数据、Gaussian、运动、渲染、语义、loss 或 cache。这样 AI 才能检查上下游是否闭合。

### 12.2 要求 AI 区分事实、推断和疑点

可直接使用：

```text
阅读这些文件后，把结论分成三类：
1. 代码直接证明的事实；
2. 根据命名或论文做出的推断；
3. 需要运行才能确认的问题。
所有事实给出文件与函数名。遇到 TODO 或分支不完整时明确指出，不要替代码补设定。
```

这对研究代码尤其重要，因为注释、README、实验脚本和当前实现可能不同步。

### 12.3 让 AI 做 shape audit

```text
以 B=1,T=4,V=3,H=160,W=240,patch_size=8 为例，审计
prepare_inputs_and_targets -> Aggregator.forward -> SLARM.forward_gs_predictor
-> SLARM.forward_renderer 的所有 reshape/rearrange/repeat。
列出每个张量的 shape，并指出任何依赖整除、视角顺序或 contiguous memory 的隐含前提。
```

shape audit 往往比泛泛解释更容易发现真正的理解错误。

### 12.4 让 AI 比较“默认值”和“实际实验值”

```text
比较 main_slarm.py 的 argparse 默认值与 training.sh 实际传参。
按“改变网络结构、改变监督、改变数据、只影响日志/性能”四类整理，
并说明最终生效值。环境变量也要纳入分析。
```

### 12.5 修改前让 AI 做影响分析

```text
我准备修改 <函数/字段>。请先用 rg 找出它的所有生产者、消费者、shape 假设、
训练/推理差异和 GPU/NPU 分支。先给影响面与最小验证方案，不要立即改代码。
```

## 13. 用运行结果校验理解

不要只相信静态解释。最低成本的验证顺序如下。

### 13.1 静态检查

```bash
python -m py_compile \
  main_slarm.py engine_tools.py inference.py inference_stream.py \
  src/models/slarm.py src/models/stream_session.py \
  src/dataset/datasets.py src/dataset/data_utils.py src/utils/losses.py
```

### 13.2 查看实际配置

训练或推理启动后，入口会把参数写到：

```text
work_dirs/<project>/<exp_name>/args.json
```

分析实验时优先读取该文件，而不是凭 shell 脚本猜测，因为脚本可能后来被修改。

### 13.3 对一个 batch 打印“契约”，不要打印全部数据

临时调试时只输出：

```python
def tensor_contract(d):
    return {
        k: (tuple(v.shape), str(v.dtype), str(v.device))
        for k, v in d.items()
        if isinstance(v, torch.Tensor)
    }
```

分别检查 `data_dict`、`input_dict`、`target_dict`、`gs_params` 和 `render_results`。不要打印完整 tensor；海量数值不会增加理解。

### 13.4 最小数值检查

重点观察：

```text
depths:       是否为正，是否大量贴近 near/far
scales:       是否为正，是否异常膨胀
quats:        范数是否合理
opacities:    是否全部接近 0 或 1
means:        是否落在预期 FLU 坐标范围
forward_flow: 静态区是否接近 0，动态区方向是否正确
render alpha: 天空区域是否较低
```

这些统计足以定位多数“能运行但结果不对”的问题。

## 14. 常见误区与代码中的真实陷阱

1. **把 target 当成模型输入图像。** 模型看的是 `context_image`；target 主要提供待渲染的相机、时间和监督。
2. **混淆 `T` 与 `T*V`。** dataset 常把时间和相机展平，进入模型前才恢复。
3. **混淆 ray depth 与世界坐标。** `means` 由 ray origin、direction 和 depth 构造。
4. **把 MS3 参数当场景流。** 它们先经时间多项式解码，之后才能得到特定时刻的 flow。
5. **忽略训练/推理分支。** `self.training` 会改变渲染通道、流输出、保存行为和部分后处理。
6. **忽略 import-time 环境变量。** `FEAT_DIST`、`OVERFIT_EXP`、`DEVICE_TYPE` 等在模块导入时就决定分支。
7. **只看 argparse 默认值。** 实际 shell 脚本覆盖了大量关键结构参数。
8. **认为 window 只裁剪输入。** 它还裁剪 KV cache，并影响 Gaussian 时间 mask。
9. **看到异常样本却不知道被替换。** dataset 的 `__getitem__` 捕获异常后会尝试下一场景，日志中的 scene id 才能揭示数据问题。
10. **直接深挖第三方实现。** 除非在修改 LSeg、Depth Anything 或 rasterizer，否则先把它们当作有明确输入输出契约的依赖。

## 15. 阅读完成后的自测题

不看代码，尝试回答：

1. 为什么只靠一张 context 图像的每个像素就能确定一个 3D Gaussian 的中心？还缺哪个预测量？
2. `context_time` 为什么先除以 `timespan`，渲染时又乘回来？
3. `patch_start_idx` 改错会同时破坏哪些 head？
4. 开启 `use_pred_camera_pose` 还必须开启什么？为什么？
5. `forward_ms3` 与 `rendered_flow` 有什么区别？
6. 为什么 target 图像不传入 `SLARM.forward()`，却仍可训练 RGB 重建？
7. sky token 为什么与 alpha 一起使用？
8. GPU 与 NPU 的 feature supervision 为什么可能走不同路径？
9. window 模式如何限制显存增长？它又如何改变时间可见性？
10. 文本查询为什么可以使用训练时从未作为固定类别定义的新词？

若能结合函数名与 shape 回答其中八题，就已经掌握了项目主干。之后阅读任何局部实现，都应先把它放回“数据 -> token -> Gaussian/运动/特征 -> 时间变换 -> 渲染 -> loss”这条链上。
